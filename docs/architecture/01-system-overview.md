# 1. System overview

## Three services, one repository

| | web | api | runner |
|---|---|---|---|
| Job | draw, interact, work offline | content, grading, progress, XP | compile and run Java |
| Tech | React 19, TypeScript, Vite, MDX | Spring Boot 4.1, Java 21, JPA, Flyway | Spring Boot 4.1, Java 21, javax.tools |
| State | browser only (offline mode) | Postgres (H2 in dev) | none |
| Talks to | api | Postgres, runner | nothing |
| Exposed | yes (port 80 behind nginx) | via web's `/api` proxy | **never** (internal network) |
| Scales by | CDN | more stateless replicas | more replicas, CPU-bound |

Why split (ADR 0001):

- **Blast radius.** Running a learner's code is arbitrary code execution. It must not happen in the process that
  holds the database credentials.
- **Different scaling profiles.** The api is light and steady; runs are CPU-heavy and bursty.
- **Independent failure.** If the runner dies, reading, quizzes and XP keep working; code blocks fall back to their
  verified output.

Why one repository: the API contract, both ends of it, and the content usually change together. One commit, one
review, no version skew.

## Folder map

```

services/runner/     Spring Boot runner (Maven wrapper)

infra/docker-compose.yml

```

## How the pieces are stitched together

1. **Contract:** `docs/api/openapi.yaml`. The web generates its types from it; the api has a test that its controllers
   serve exactly those paths.
2. **Content:** `content/` is read by the api at start-up (`FileSystemContentSource`) and bundled into the web build
   (`bundledContent.ts`). Same files, same defaults.
3. **Runtime wiring:** the browser calls only `/api/v1/*`. In dev, Vite proxies that to the api; in Docker, nginx does.
   The api calls the runner at `STACKCRAFT_RUNNER_URL` through the `CodeExecutor` port.
4. **Correlation:** every request gets an `X-Request-Id` (nginx `$request_id`, or generated by the api's filter). It is
   logged on every line and forwarded to the runner, so one id traces a Run click across all three services.

## Interview angle

"Design an online code judge." The answer starts here: separate the untrusted-execution tier, put a queue with
backpressure in front of it, never let it near data or secrets, and keep the rest of the product working when it is
down.
